## P2 - API y diseno futuro

- [ ] Considerar tipos fuertes para buffers de decode.
  - El orden `inputBuffer`, `frameBytes`, `payloadInFrame` es facil de confundir.
  - Una estructura `ProtocolDecodeBuffers` podria hacer mas clara la llamada.

- [ ] Considerar una API que devuelva tamanos reales sin obligar a sobreasignar.
  - Para decode COBS/R, el payload real solo se conoce despues de decodificar.
  - Puede valer la pena exponer un flujo en dos pasos o un decoder que use un scratch buffer administrado por el usuario.

- [ ] Evaluar versionado de protocolo mas explicito.
  - `Frame::Actual_Frame_Version` es constante.
  - Si habra compatibilidad con versiones futuras, definir tabla de versiones, migracion o rechazo por feature flags.

- [ ] Evaluar mapa de compatibilidad `PackageKind` x `MessageType`.
  - Hoy todo kind valido con todo type valido es aceptado.
  - Si hay combinaciones invalidas a nivel semantico, esa politica pertenece a otra capa o debe entrar explicitamente al decoder.
